# 框架主题深度拆解 · 工作流

> **这个 skill 不输出文章。它输出"完整、可口头复述的理解"。**
> 输入：一个框架/代码库 + 一个主题词
> 产出：4 份结构化 markdown 文档
> 写文章是 skill 结束之后的事。

---

## 适用 / 不适用

✅ 适用：
- 准备写技术分享 / 公众号 / 团队讲座，但还没完全摸清主题
- 主题跨多个模块（不是单文件可解释的）
- 想要"完整不漏"地理解某个子系统

❌ 不适用：
- 单文件、单函数问题 → 直接 Read / Grep
- 调试具体 bug → 用 debugging skill
- 设计新功能 → 用 brainstorming → writing-plans

---

## ⚠️ 核心基础原则：不猜 → 先 Read → 再问

**这条原则凌驾于一切阶段流程之上，是这套方法论可信度的根。**

**所有结论必须有依据**——要么是读到的代码 / 文档 / 数据文件，要么是用户明确告知。**禁止用 "通常"、"一般来说"、"应该是"、"按惯例"、"大概率" 这类先验知识填空。** LLM 训练语料里有大量同类框架的"通用模式"，这些模式很可能跟当前项目实际实现不同——靠常识猜出来的结论是这套方法论最大的污染源。

### 不确定时的决策顺序

```
遇到不确定
  │
  ├─[1]─→ Read 相关文件
  │       （源码 / README / 测试用例 / 样本数据 / config / 注释）
  │       └─→ 读到了 ──→ 把结论写进产物，附 file:line 引用
  │
  ├─[2]─→ 文件里找不到，扩大搜索范围
  │       （rg / git log / git blame / 历史 RELEASE_*.md）
  │       └─→ 找到了 ──→ 同上，附 file:line / commit-hash 引用
  │
  └─[3]─→ 仍找不到 ──→ 问用户
          - 明确说："我已经查过 X / Y / Z 都没找到"
          - 不要让用户自己去找，给出具体问题
          - 用户答复后回填到产物里，注明 "据用户 {date} 告知"
```

### 必须显式标注的两种情况

1. **依据不足但需要给出阶段性产物**：用 `[待澄清: ...]` 标记，写进当前阶段的"待澄清问题"列表，**不要混在正文里假装是结论**
2. **跨阶段假设**：阶段 1 时为了推进做了某个假设、留到阶段 2 验证 → 在阶段 1 产物末尾的"假设清单"里列出，阶段 2 开头先逐条验证。

#### ⚠️ 假设清单准入闸

**下笔写"假设"前必答**："如果我现在就 Read 那个文件，能不能 5 分钟内验证？"  
能 → **必须现在去 Read**，不准写进假设清单。读完写进正文带 `file:line` 引用。

✅ **合法假设**（无法在阶段 1 当场验证，才能写入清单）：
- 依赖**运行时行为**才能验证（如"`on_memory_write` 在每次 memory tool 写入后触发"——需观察运行时调用栈或测试用例）
- 依赖**用户决策**（如"假设外部依赖 X 不算本主题核心，归到剔除"）
- 依赖**跨模块综合判断**（如"假设这 3 个文件构成一个完整子系统，无遗漏成员"——需要阶段 2 深挖才能确认）

❌ **非法假设**（伪装成假设的偷懒，发现一例打回）：
- "文件 X 第 Y 行的具体内容是 Z"——必须当场 Read，Read 失败再问用户
- "schema 大致是 ..."、"接口大概返回 ..."——同上
- 已有 `file:line` 引用的事实——那是**已验证结论**，挪到正文，不属于假设清单

### 反模式示例

| 错误（猜） | 正确（先 Read 再下结论） |
|---|---|
| "Hermes 应该用 SQLite 存会话" | "经 Read `gateway/storage.py:42-58` 确认，使用 SQLite，schema 见 state.db" |
| "记忆通常分热/冷两层" | "Read `MemoryManager` 全文件未发现分层抽象 → `[待澄清: 是否存在运行时分层?]`" |
| "Provider 模式一般都用工厂注册" | "Read `agent/memory/registry.py:10-45`，确认通过 plugin discovery 加载" |

### 自检触发词

写产物时如果出现以下词汇，**立刻停下来**，要么补 Read 找到依据，要么改写成 `[待澄清: ...]`：
- 通常 / 一般 / 大概率 / 应该 / 估计 / 想必 / 按惯例 / 类似 XX 框架
- "我认为" / "我猜" / "可能是"

## ⚠️ 可视化产出强制要求

**纯文字 + 表格不算合格产出。每个阶段必须包含至少一张 Mermaid 图。**

**为什么强制**：文字描述能让人产生"我以为我懂了"的错觉，而画图强迫你把模糊的关系具象化。一旦动笔画连线，画不出来的地方就是真正的盲区。**画图是发现漏洞最高效的工具，不是装饰。**

### 各阶段必含图

| 阶段 | 必含图（至少 1 张） | Mermaid 类型 | 作用 |
|---|---|---|---|
| 0 | （可选）关键词概念图 | `mindmap` 或 `flowchart` | 主题复杂时用，看关键词之间的语义关系 |
| 1 | **子系统关系图**（必含）+ **文件归属图**（必含） | `flowchart TB/LR` | 看清模块怎么切、谁调谁、文件落在哪个子系统 |
| 2 | **数据生命周期图**（每个子系统 1 张） | `flowchart LR` | 生产点 → 存储介质 → 消费点 → 提供接口 的全链路 |
| 3 | **架构总图**（必含） | `flowchart` | 跨子系统调用 / 数据流的统一视图，所有边带名字 |

### 画图守则

1. **Mermaid 优先**，理由：纯文本可 diff、可 git 追踪、所有 markdown 工具都能渲染、Claude 写起来比 SVG 快一个数量级
2. **图嵌在阶段产物的 markdown 里**，不另存文件（除非超过 30 个节点）
3. **画完图自检**：能不能用图本身（不看正文）回答"这个子系统跟谁有依赖关系？"答不上就改图

### 制图细则

**节点数量按图类型分级**：

| 图类型 | 节点上限 | 理由 |
|---|---|---|
| **全景级**（Phase 1 子系统关系图 / 文件归属图、Phase 3 架构总图） | **无硬限制** | 这是"唯一一张说明全貌的图"，越详细越清晰；模型读图比人读图更不受节点数影响 |
| **流程级**（Phase 2 数据生命周期图） | **≤ 25**（软上限） | 按顺序读，可承受更多节点；超 25 建议拆图但不强制 |
| **单子系统细节图**（如某子系统的内部状态机） | **≤ 18** | 单一焦点应当紧凑 |

**节点数硬限被替换为"质量门"**——只要满足以下质量门，节点数可以多：
- 所有节点都隶属某个 subgraph（不允许悬空在主图根，除非节点本身代表"外部 actor"如用户/外部服务）
- 每条边都有标签（见词汇表）
- 无孤立节点
- subgraph 嵌套不超过 3 层
- 同向边不交叉（用 `direction TB` / `LR` 强制走向；交叉超过 5 处说明布局乱，要调整）

**反过来——节点太少也是问题**：
- 全景图低于 8 个节点很可能是"高度抽象成空壳"，要回头检查是不是漏画了关键关系

**视觉顺序**：
- subgraph 排列必须**与子系统编号一致**（S1 → S2 → S3 ...）。
- 不允许按"重要性 / 调度优先"重排——破坏读者寻找子系统的肌肉记忆。

**边标签词汇表**（每条边必须用以下一类，禁止混搭中文动词）：
- **函数调用**：`fn_name()` 或 `fn_name(args)`
- **数据流**：`写入 X` / `查询 X` / `返回 X`
- **事件钩子**：`on_xxx 钩子` / `事件: xxx`
- **关系类型**：`实现` / `继承` / `镜像` / `注入` / `订阅` / `调度`
- ❌ 禁止：纯中文动词无对象（如裸"实现"）、计数描述（如"8 个具体实现"）、多语义混叠（如"format_for_system_prompt + 冻结快照"——拆成两条边或选一个主语义）

**孤立节点禁令**：
- 任何 subgraph 或节点出现就必须有边连进或连出。
- 孤立节点 = 信息冗余 = 必须删除或补连接。
- 检查方法：画完后扫一遍每个节点，找不到任何 `--> X` 或 `X -->` 的就是孤立。

**箭头语义**：
- 实线 `-->`：直接同步调用 / 写入
- 虚线 `-.->`：弱依赖 / 事件回调 / 异步通知 / 共享数据

### 反模式

❌ 用 ASCII art 凑数代替 Mermaid（除非该环境真的不支持 Mermaid）
❌ 画了图但跟正文表格内容不一致（图跟字必须严格同步）
❌ 把所有信息都塞一张图——拆开，每张图回答一个问题
❌ 画图时给自己留"以后补"——不画完不能进下一阶段

## ⚠️ 阶段间回顾机制：单向流水线是错的

**这套方法论不是单向管道，是带反馈的循环。每完成一个阶段或阶段内的里程碑，必须回头检查上游产物。**

### 为什么需要

后续阶段总会发现上游"猜对了哪一处 / 漏了哪一处 / 切歪了哪一处"。不主动回头：
- 错误留在上游产物里，下次读时还要重新踩坑
- 没有 diff 记录，复盘时不知道为什么改
- 把"反向修正"留到最终阶段做，越积越多越改不动

### 固定回顾触发点

| 触发点 | 检查对象 | 必做动作 |
|---|---|---|
| 完成 1a 心智模型 | 种子卡 `00-seed.md` | 把项目专属词汇补进核心关键词 |
| 完成 1b 热力图 | 种子卡 + 1a | 高命中关键词回填、未命中关键词标注或移除 |
| 完成 1c 决议 | 种子卡显式排除 | 把剔除项的精准措辞补进显式排除 |
| 完成 1d 全景图 | 1a / 1b 产物 | 子系统边界是否要回头调整心智模型表 |
| **完成每张 Phase 2 卡** | **v0 + Phase 1 全景图** | **在卡末尾写"对上游产物的影响"小节**（必填，无影响也要显式"无"） |
| 完成全部 Phase 2 卡 | v0 → v1 综合 | Phase 3 开场强制做 v0 → v1 升级，每处变化带 `[diff]` 标记 |
| 完成 Phase 3 综合 | 全部上游产物 | 在 `03-synthesis.md` 的 **3.4 上游回填决议表**逐行处置（修文件 / 进 amendments / 进 Rejected）；子代理验证产出"反向 amend 建议"并入此表 |

### Amend 规则（不重写，加记录）

发现上游需要更新时，按修订类型走不同路径：

| 修订类型 | 处理方式 |
|---|---|
| **小修订**（错别字、缺失引用、补 `file:line`） | 直接改原文件；git commit message 注明"amend from Phase X" |
| **结构修订**（子系统边界变了、新增/合并子系统） | **不重写原文件**，新增 `0X-amendments.md` 记录差异和理由，原文件保留供回查 |
| **抽象层变化**（v0 → v1） | 写入 Phase 3 产物开头，每处变化标 `[diff v0→v1: 修正/新增, 来自 Sx]` |

### Phase 2 每张卡末尾必含小节

`## 回顾：对上游产物的影响`，必含 4 行（无影响也要显式写"无"）：
- ✅ **确认 v0**：本卡哪些发现支撑 v0 的哪一处主张（具体到 v0 里的字句）
- 🔁 **修正 v0**：本卡修正了 v0 的哪句话（用 before → after 形式）
- ➕ **新增维度**：本卡发现了 v0 没覆盖的维度（必须显式标记，否则 Phase 3 又会"突然发现"）
- 📝 **回填 Phase 1**：若本卡发现 Phase 1 全景图或子系统清单有错漏，列出需 amend 的具体项；放到 `01-panorama-amendments.md`

### Phase 3 开场必跑步骤

进入 3.1 架构总图之前**强制**先做：

1. **收集 diff**：把所有 Phase 2 卡末尾"回顾"小节的 🔁 修正 + ➕ 新增维度 + 📝 回填 全部汇总
2. **v0 → v1**：基于 diff 重写抽象，写入 `03-synthesis.md` 开头作为 `## 核心抽象 v1`
   - 每处变化标 `[diff v0→v1: <修正/新增>, 来自 S<n>]`
   - v0 原文保留在下方作为对照
3. **Phase 1 回填决议**：扫一遍 `01-panorama-amendments.md`，决定哪些进入 amendments、哪些直接修改原文件
4. v1 通过后才能开始 3.1 架构总图——不允许跳过这一步直接画图

### 不允许的反模式

❌ "我等 Phase 3 再统一改" —— 错误堆积越久越改不动，最后变成"重写"而不是"迭代"
❌ 直接改上游产物但不留记录 —— 下次复盘没有任何依据
❌ "本卡对 v0 无影响" 的占位填法 —— 必须明确说哪一句话被支撑/未被支撑，强迫思考一遍
❌ Phase 3 直接画架构总图，跳过 v0 → v1 综合步骤

## ⚠️ 验证机制：用干净上下文子代理交叉检查

**规则补不完。每个阶段的产物必须经独立子代理验证，让无污染的眼睛重新对照源码。**

**🔒 命根子（凌驾本节所有细则）：每一次验证都是一次全新、无污染的子代理调用。** 任何复用、续接、`SendMessage` 接力一个"已经见过待验证文件或主对话"的子代理，都视为验证失效——因为干净上下文是整套机制唯一的价值来源（见下"为什么用子代理"）。一旦子代理带着上一轮的判断进来，它会维护旧结论、跳过重新 Read，退化成主代理自验证。**"全新子代理"不是建议，是过线条件。**

### 为什么用子代理而不是加规则

主代理写产物时受自身上下文污染：
- **同样的浅读 → 同样的浅结论**（只看 `if len(matches) > 1` 没看 else 分支）
- **同样的常识填空 → 同样的盲区**（"通常都是..."）
- **已写下的判断形成路径依赖**——回头自查时眼睛会"跳过"已经写过的地方

干净上下文的子代理：
- 没读过你写的卡 → 不知道你想得出什么结论
- 必须从源码出发重新建立判断 → 容易抓到"条件性 fallback"这类隐藏分支
- 子代理报告什么都不知道，所以**只能引用源码原文**说话

### 验证触发点（每阶段强制）

| 触发点 | 验证什么 | 子代理类型 | 报告产物 |
|---|---|---|---|
| 完成 Phase 1 全景图（**首验**）| 子系统清单 / 剔除证据 / 关系图 / 文件归属图 vs 源码 | general-purpose | `01-panorama-verification.md` |
| **完成每张 Phase 2 卡** | 该卡所有事实声明 vs 源码 + **vs panorama 一致性** | general-purpose | `02-{name}-verification.md` |
| 全部 Phase 2 卡完成后（**panorama 复验**）| panorama 与所有 Phase 2 卡的跨文档一致性 | general-purpose | `01-panorama-cross-verification.md` |
| 完成 Phase 3 综合 | v1 抽象 / 架构总图 / 跨子系统模式 / 跨卡矛盾决议 / 上游回填项 vs 源码 + Phase 2 卡 | general-purpose | `03-synthesis-verification.md` |

**为什么 panorama 要验两次**：第一次（首验）只能对源码核单文档内一致性；但 panorama 经常会把 S? 的符号挂错到 Sx 下（如 `_format_memory_result` 错配给 S2），这种**跨文档归属错**只有在 Phase 2 卡都写完后才能 cross-check。所以 panorama 必须二次验证。

**Phase 2 卡验证特别约束**：调用模板时**必须传入 panorama 路径作为"关联文档"**，子代理会执行模板第 5 步——跨文档一致性检验，抓 panorama 与该卡的不一致。

**Phase 3 综合验证特别约束**：调用模板时**必须传入 panorama 路径 + 全部 Phase 2 卡路径**作为"关联文档列表"，并在 prompt 末尾追加这段：

```

### 反向 amend 建议（必含小节）
基于本次综合发现，列出 panorama 或 Phase 2 卡需要根据 Phase 3 修订的项：
- [BACKFILL-<source>-<target>] 综合层 v1 / 总图 / 模式 / 矛盾决议 与 <上游产物> 哪一条不一致 / 建议改法
- 例：[BACKFILL-v1-S6] v1 引入"frozen-snapshot"模式，S6 卡末尾"设计取舍"段未提此模式 / 建议补一条
- 若无，显式写"已扫所有 v1 论断 / 总图边 / 模式 / 矛盾决议 vs 上游，无反向 amend 项"

- 跨子系统模式 vs 每张 Phase 2 卡的"设计取舍"
- 跨卡矛盾决议 vs 涉及卡的相关段落

### 跨子系统模式硬门检查（必含小节）
对 3.2 列出的每个"跨子系统模式"，逐条验证其"出现位置"：
- 列出该模式的全部出现位置归属的子系统集合
- 若 |子系统集合| < 2，标 [BLOCKER]：模式 X 仅出现在子系统 Sn 内部，不符合"跨子系统"定义
- 例：模式 skip-on-interrupt 出现在 `:5891` + `:2000`，两处都归 S6 → [BLOCKER] 不是跨子系统模式，应降格为 S6 局部设计或补真正跨系统的位置

### 3.4 回填表完整性核对（必含小节）
对比验证报告本身的 `[BACKFILL-*]` 数量 vs 3.4 表里 `验证 BACKFILL` 行数：
- 数量不匹配 → 标 [BLOCKER]
- 检查 `## Rejected verifier findings` 段是否被误用（是否出现"采纳并修"字样）→ 标 [MUST-FIX]
- 检查 `## Rejected verifier findings` 段是否在无拒绝时显式写"无"→ 缺失则标 [MUST-FIX]
```

主代理收到验证报告后：
- **反向 amend 建议**逐条进入 3.4 上游回填决议表，**禁止以"已综合"为由忽略**
- **跨子系统模式硬门**的 [BLOCKER] 必须修——要么删模式，要么补真正跨系统的位置
- **3.4 表完整性 + Rejected 段规范**的发现按常规 [MUST-FIX] 处理

### 子代理调用模板

主代理用 Agent 工具调用，prompt 模板如下（替换 `{占位符}`）：

```
你是一个验证子代理。你从未见过这张卡或主对话——这是关键。你的任务是用完全新鲜的眼睛把卡的声明对照源码逐条核对。

待验证文件: {绝对路径，如 .../02-builtin-file-memory.md}
项目根目录: {绝对路径，如 /mnt/d/project/github/hermes-agent}
关联文档（用于跨文档一致性检验）: {可选，如 panorama 路径——见下方第 5 步}

协议：

1. **通读卡一遍**，列出所有事实声明（不只是元数据，包括设计取舍里的因果陈述）

2. **逐条核对，按类别用不同手段**：

   a. **file:line 声明**（"MemoryStore class at memory_tool.py:107-460"）
      → Read 该范围，确认起止行号是否真实包含所述内容（很多卡的结束行号是估算）

   b. **数字声明**（"12 种威胁"、"9 个核心方法"、"默认 2200 字符"）
      → **不要相信卡的数字**。用 grep/wc 或 Read 重新计数，对比。

   c. **条件逻辑**（"X 时拒绝"、"scan 发生在写入前"）
      → **读完整个 if/elif/else 链**，不能停在第一个分支。
      → 例："多匹配拒绝" 要检查是否有 `if all_identical: fall_through` 这种 fallback

   d. **跨文档引用**（"被 S3 调用"、"暴露给 ACP"）
      → 验证引用的子系统/符号确实属于声明的归属

   e. **数据流声明**（"生产 → 存储 → 消费"）
      → 沿代码追写入点和读取点，对照生命周期图（如有）

3. **主动找下列盲区**：
   - 没附 file:line 的"通常/一般/应该"陈述
   - 闻起来圆整的数字（"~50"、"大约 170"）
   - 可能有边界情况的条件动词（"拒绝"、"跳过"、"屏蔽"）
   - 容易和同文件兄弟函数混的函数名

4. **最低覆盖**：
   - 报告里 ✅ + ⚠️ + 🔴 + 🔍 总条数应 ≥ 卡里事实声明数的 **70%**。
   - 低于 70% 算漏检，不准结束。
   - 报告字数 600 字是**上限不是下限**。**300 字以下必须自检**："我是不是漏了'设计取舍'段？是不是没数关键定义点？"

5. **跨文档一致性检验**（仅当传入"关联文档"时执行）：

   **不能停在"文件路径是否一致"层面**——必须深入到行号 + 符号名：

   - **a. 文件路径**：panorama 列了但 Phase 2 卡没有的文件（或反之）→ ⚠️/🔴 视严重程度
   - **b. 行号范围**：同一文件在两份文档里行号不同（如 panorama 写 `:582`，卡写 `:551-579`）→ 至少列 ⚠️，让 main agent 判断是真冲突还是同文件不同切片
   - **c. 函数名 / 符号名**：同文件不同函数指代不同子系统的关键面——这是最隐蔽的归属错。例：
     - panorama S2 关键文件：`acp_adapter/tools.py:582`（`_format_memory_result`）
     - S2 卡涉及文件：`acp_adapter/tools.py:551-579`（`_format_session_search_result`）
     - 同文件不同函数 → **panorama 把 S1（memory tool）的 ACP formatter 错配给了 S2** → 必须 🔴 [BLOCKER]

   **跨文档检验自检题**：每个声明都问"这个符号在另一份文档里也出现吗？如果是，引用的是不是同一个具体定义？"
   只比 path 不比符号 = 漏检

6. **输出报告**（markdown，写到 stdout 由主代理保存到 verification.md）：

   ## 验证报告：{文件名}

   ### ✅ 通过的声明
   - 声明 — 验证依据 `file:line` 或命令
   （如果一条都没列，说明你没认真核对，重跑）

   ### ⚠️ 轻度偏差（行号尾巴、措辞、计数微差）
   每条带 **状态标签**：`[MUST-FIX]` 或 `[OPTIONAL]`，由你判断
   - [MUST-FIX] 卡说：... / 实际：... / 修法：...
   - [OPTIONAL] 卡说：... / 实际：... / 修法：...

   （如果"无"，显式写"无（已逐条核对）"——不允许直接省略本节）

   ### 🔴 实质错误（事实/逻辑/归属错，会误导读者）
   每条带 `[BLOCKER]` 标签
   - [BLOCKER] 卡说：... / 实际：... / 证据：`file:line` + 代码片段 / 修法：...

   （如果"无"，显式写"无"）

   ### 🔍 可疑/未能验证
   每条带 `[NEEDS-MANUAL-VERIFY]` 标签
   - [NEEDS-MANUAL-VERIFY] 声明：... / 为何可疑：... / 验证需要什么：...

   **🔍 不允许永远为空**——600 字预算内一定有跨文件、运行时、跨架构声明无法当场验证。
   如果你写"🔍 节：无"，请额外回答："我对所有事实声明都做了主动验证还是只验证了显眼的？"
   答不上来 = 这一节漏了。

   ### 总结（强制 4 行）
   - 通过率：N/M（如 22/28）
   - BLOCKER 数：N | MUST-FIX 数：M | OPTIONAL 数：K | NEEDS-VERIFY 数：P
   - 字数：约 N 字（自检：≥ 300 字否？）
   - **建议下一步**（三选一，必须明确写）：
     - 直接进下阶段：无 BLOCKER，MUST-FIX 全部 OPTIONAL 化
     - 修完再进：有 BLOCKER 或 MUST-FIX
     - 修完重跑验证：BLOCKER ≥ 3 或涉及结构性错误（如生命周期图顺序错、跨文档归属错）

约束：
- **禁止 Edit/Write 任何文件**。Read 和 Bash（grep/rg/wc）only。
- 每条发现都必须引用 `file:line`。
- 不要复述卡的内容——只报发现。
- 条件逻辑要狠——这是主代理最大盲区。
- 报告控制在 **300-600 字**之间。
- **禁止使用"已修"措辞**——你只 Read，没权限改。"已修"由 main agent 在落盘卡时另行记录。
```

### 验证报告处理

1. 子代理输出的报告保存为 `0X-{name}-verification.md`（同目录）
2. 主代理按 status label 逐条处理：
   - `[BLOCKER]` — **必修**，修完才能进下阶段
   - `[MUST-FIX]` — 必修（虽然不阻塞下阶段但不允许累积）
   - `[OPTIONAL]` — 可选，但必须显式标 "暂不修，理由：..."，不能装没看见
   - `[NEEDS-MANUAL-VERIFY]` — 人工判断要不要再 Read 一次源码或问用户，**不能默默放过**
3. **修完不允许在 verification.md 里写"已修"**——verification.md 是子代理的客观报告，是只读快照。
   主代理回填时另开两段（写在卡片末尾或独立 `0X-fixes.md`）：

   `## Fixes applied after verification`（逐条记录修补）
   - "针对 [BLOCKER #1]，修改了 `02-X.md:L97`，原文 X → 新文 Y"
   - "针对 [MUST-FIX #2]，修改了 `02-X.md:L11`，原 :10965-10983 → :10959-10983"
   - "针对 [OPTIONAL #1]，**暂不修**，理由：差异在 1 行内不影响理解"
   - "针对 [NEEDS-MANUAL-VERIFY #1]，已查证：`memory_tool.py:55-57` `get_hermes_home()` 是运行时 env 解析，结论是 X"

   `## Rejected verifier findings`（**当主代理不同意验证者**时必填）
   - "针对 [BLOCKER #N]，验证者建议修法 X，主代理改用 Y。理由：..."
   - 例："验证者建议方法计数改 10+6+2（数全部 def），主代理改用 7+6+2（用 docstring 标称数）。理由：docstring 是设计意图的权威表述，源码 def 数包含 property 等非'方法'语义"
   - **不允许偷偷绕过**——任何与验证者建议不一致的修法都必须有书面理由
   - **本段只用于"拒绝/分歧"**，不允许写"采纳并修"——采纳的建议属于 fixes log（写在 `## Fixes applied after verification`）或 3.4 上游回填表，**不进本段**
   - **无拒绝时必须显式写**："无 rejected findings——所有验证者建议均已采纳并进入 fixes log / 3.4 上游回填表"
   - 段被误用（在本段里写"采纳并修"）会让审核读者认知混乱、真分歧无处可写——这是反模式，下次验证子代理会标 [MUST-FIX]

4. **所有 [NEEDS-MANUAL-VERIFY] 都必须有显式处置**，三选一：
   - "已查证 + 结论"（附 file:line / 命令）
   - "已问用户 + 答复"（附日期）
   - "暂搁，理由：..."（必须有具体理由，不能是"以后再说"）
   
   没处置 = 阶段没过线。**最常见偷懒：把 NEEDS-VERIFY 视为可选，结果跨阶段越积越多。**

5. 如果 BLOCKER ≥ 3 或子代理建议"修完重跑验证"，**修完后必须重跑一次验证子代理**——单次验证可能因第一批修补引入新问题
   - **重跑必须是全新子代理**（重新发起 `Agent` 调用），**禁止用 `SendMessage` 续上原验证代理**：原代理已经下过判断，会维护旧结论、不会真的重新对照源码，等于没重跑

### 跨文档归属错：最容易漏的盲区

panorama 把符号 X 挂在子系统 Sa，但 X 实际属于 Sb——这种**跨文档归属错**单看任何一份文档都看不出来，必须 cross-check 时才能发现。例：

> panorama 在 S2（会话存储与搜索）的"关键文件"里列了 `acp_adapter/tools.py:582`（`_format_memory_result`）——但 `_format_memory_result` 实际是 S1（内置文件记忆）的 ACP formatter。S2 的真正 formatter 是 `_format_session_search_result :551`。

这就是为什么验证机制设计成"Phase 2 卡验证时传入 panorama 路径 + Phase 2 全部完成后再做一次 panorama cross-verification"。**单文档内核对永远抓不到这种错。**

### 不允许的反模式

❌ 跳过验证直接进下一阶段 —— 验证不是"加分项"，是过线项
❌ 用主代理自验证 —— 同上下文 = 同盲区，等于没验证
❌ **把多张卡塞进一个子代理一起验** —— 卡间上下文互污、深度被摊薄，违背干净上下文命根子。**一张卡 = 一次独立调用**（Phase 2 每张 `02-*.md` 各起一个全新子代理）
❌ **修完重跑时 `SendMessage` 续上原验证代理** —— 原代理带着旧判断，重跑也抓不出新问题，见上"验证报告处理"第 5 条
❌ 看完报告但不动 🔴 错误 —— 等于知道有坑还要踩
❌ 把验证报告当 noise 不存盘 —— 下次会话主代理找不到上次的发现

### 验证是规则的兜底，不是规则的替代

skill 里写的具体规则（"无约数词"、"file:line 必填"、"剔除项有具体证据"）仍然要遵守——它们是**基线**，能让主代理写得更规范。但规则只能拦住已知错误模式；子代理验证的价值在于**抓到未列入规则的错误模式**。两者互补。

## 阶段 1：A+B 全景扫描

**核心思想**：
- **A（自顶向下）**：项目结构告诉你"按设计该看哪里"
- **B（自底向上）**：关键词命中告诉你"实际代码在哪"
- **两者差异处就是宝藏**——盲区或误判

**严格 4 步顺序**（不可并行，因为 1a 的产物会回填到 1b 的关键词）：

### 1a. 项目心智模型扫描

**为什么必须先做**：项目专属词汇会让 1b 关键词更准。例如 Hermes 里可能用 "context_compre[ssion]"、"account_usage" 等本项目特有词，不读文档抓不到。

**动作**：
- Read：README / README.zh-CN / AGENTS.md / docs/ 目录 1-2 篇综述类文档
- Bash：
  - `ls` 看根目录
  - `find . -maxdepth 2 -type d -not -path '*/\.*' -not -path '*/node_modules*'` 看二级目录
  - `git log --oneline -20` 看近期重心
  - `find . -name "*.md" -not -path "*/node_modules/*" -not -path "*/.git/*" | head -30` 列文档

**`01-mental-model.md` 必含小节**：
- `## 一段描述`：200 字内说清项目是干什么的、核心抽象、入口点、当下重心
- `## 顶层目录角色`：表格，列：目录 / 角色
- `## 项目专属词汇`：bullet 列表，回填到种子卡的关键词补充进去

完成后**回到 `00-seed.md` 把新发现的项目专属词汇补进核心关键词**。

### 1b. 符号反向追踪

**动作**（对种子卡里每个关键词跑一遍，包括大小写敏感版本）：
- `rg -n "<keyword>"` — 全仓搜
- `rg -c "<keyword>" | sort -t: -k2 -nr | head -30` — 按文件聚合命中数
- `rg -l "<keyword>" --type-add 'data:*.{json,yaml,yml,jsonl,db,sqlite,toml}' -t data` — 找数据/配置文件
- `rg -n "^\s*(class|def|fn|func|async def)\s+\w*<keyword>\w*" -i` — 找定义点

**`01-heatmap.md` 必含小节**：
- `## 执行的命令`：把本次 1b 跑过的所有 `rg` 命令贴出来，每条附该命令的命中文件数总数（如 `rg -c "MemoryProvider" | wc -l → 23`）。方便用户复跑验证。
- `## 按文件命中热力图`：表格，列：文件 / **精确命中数** / 1 行用途速写
- `## 数据 / 配置 / 文档文件`：bullet 列表，附 1 行格式说明
- `## 关键定义点`：bullet 列表，格式 `file:line — class/def name — 1 行作用`

**计数硬约束**：
- 命中数必须是 `rg -c` 输出的**精确数字**，不允许 `~50`、`大约`、`几十次`、`~170+` 这类约数
- 类似 "8 个插件" 的计数声明必须附验证命令的实际输出（如 `ls plugins/memory/ | wc -l → 8`）
- 约数词（`大约` / `左右` / `几十` / `~N` / `N+`）触发**自检触发词**机制——见核心基础原则

**完成 1b 的检查项**：
- 种子卡里**每个**关键词都跑过 grep（不能漏）
- 至少跑过一次"找数据文件"的命令（用户特别强调"记忆涉及哪些文件，不是代码"——数据/配置/文档文件容易被漏）
- 所有计数都是精确数字，无约数词

### 1c. 交叉对照 + 盲区填补 ⚠️ 人在回路

**这一步必须用户拍板，禁止自动决策。**

把 1a 的"按结构猜测的相关目录"和 1b 的"按命中实际找到的文件"叠在一起，列出三类差异：

| 类别 | 含义 | 你的动作 |
|---|---|---|
| 1a 列出、1b 几乎无命中 | 项目结构骗了我们 | 提议"剔除"，附 1 行理由，等用户确认 |
| 1b 有命中、1a 没列出 | 盲区！通常是工具函数 / 配置加载器 / 测试夹具 / 数据初始化脚本 | 提议"纳入"，附 1 行理由，等用户确认 |
| 两者都有 | 核心模块 | 默认纳入，但仍要让用户看一眼 |

**做法**：对每个差异点产出一行**提议**（例："S2 `tools/` 提议剔除——这里只有 3 处命中且都是 docstring 引用"）。然后**让用户逐条确认**。可以一次性列完让用户批量回复，但不能跳过用户。

### 剔除项理由证据形态

每个剔除项必须附以下一类**具体证据**（写在理由括号里）：
- 经 Read `path:line-range` 确认是 X（最强证据）
- 经 `rg` 验证只有 N 处命中且都是 docstring / 注释 / import
- 经 `git log -- {path}` 确认不在主项目维护范围（如：工具自动生成、临时产物、构建副产品）
- 用户明确告知不在本次主题范围（注明 "据用户 {YYYY-MM-DD} 告知"）

❌ **不允许的剔除理由（空话，必须替换为具体证据）**：
- "不是核心" / "非核心"
- "工具性代码" / "辅助代码"
- "前端展示层" / "UI 层"（除非配 Read 证据）
- "不影响 XX 架构"（凭什么不影响？哪行代码看出来的？）

### 1e. 粒度与一致性审查 ⚠️ 进阶段 2 前必跑

写完 1d 全景图后，进阶段 2 前**必须**跑完以下三轮审查：

#### 粒度审查（针对每个纳入的子系统，3 问全 Yes 才合格）

1. 是否有 ≥ 2 个核心代码文件 **或** ≥ 2 个**一等公民数据文件**（即"该子系统是什么"的核心存在物，不是其他子系统的副产品）？
   - 例：S1 内置文件记忆只有 `memory_tool.py` 一个代码文件，但 `MEMORY.md` + `USER.md` 是它的一等公民——这种情况算合格
   - 反例：某子系统只有 1 个代码文件 + 0 个一等公民数据文件，且 README/docstring 也没把它当独立模块讲——这种是真的薄
2. 是否有 ≥ 2 条对外关系（调用 / 被调用 / 事件钩子）？
3. 是否有独立的设计意图（不只是"暴露 S? 的功能"或"是 S? 的薄包装"）？

任意 1 问 No → 提议**合并到最近的相关子系统**（如：薄薄一层"对外暴露 S2 能力"且无独立设计意图的，提议并入 S2 作为其"对外暴露面"小节）。提议后**等用户拍板**。

#### 子系统数健康区间

5 ≤ N ≤ 9。
- N < 5：可能切得太粗，回 1c 看是否漏纳了盲区
- N > 9：可能切得太细，先用上面 3 问 审查能不能合并

#### 一致性审查

**强制 checkbox 形式**（每个子系统 3 个勾必须全打上，少 1 个都算 fail）：

```
S1：[ ] 在子系统关系图  [ ] 在文件归属图  [ ] 在候选子系统清单
S2：[ ] 在子系统关系图  [ ] 在文件归属图  [ ] 在候选子系统清单
S3：[ ] ...
...
```

**额外配套检查**：
- 子系统关系图中每个 subgraph 必须能在候选子系统清单里找到对应 `### S{n}:`
- 文件归属图中每个文件必须能在某个子系统卡片的"关键文件"里找到（或在 `Shared` 子图里）
- **跨子系统共用的文件**（如 `run_agent.py` 既是 S4 的实现载体又是 S6 的调度循环）：要么用 `Shared` 子图并连边到各依赖子系统，要么在多个 subgraph 里用**带行号片段**作为节点（如 `run_agent.py:6056-6281`）区分不同切片
- 任何一处不一致 → 改图或改文字到一致为止

### 1f. 反向覆盖检查 ⚠️ 防止漏检（必跑）

**问题**：1a-1e 都是**自顶向下** + **按当前认知**找子系统。如果某个真子系统的实现"藏"在某个大文件中间段（如 `run_agent.py:4284` 的 `_spawn_background_review`），或者它是"后台路径"不在主循环调用图里，前面流程**抓不到**。

**机制**：扫"已纳入符号"的**全部反向引用**，把不在子系统归属里的引用点暴露出来。

#### 执行步骤

1. **提取核心符号清单**：把 panorama 中所有 file:line 引用涉及的核心符号（class / 函数 / 全局常量）汇总，去重得到候选符号集。例 Hermes 记忆：`MemoryStore` / `MemoryProvider` / `MemoryManager` / `memory_tool` / `MEMORY_SCHEMA` / `on_memory_write` / `format_for_system_prompt` / `_memory_write_origin` / `_memory_write_context` 等

2. **逐个符号 grep**：用 `rg -n "<symbol>"` 在整个项目跑一遍（include `*.py`，exclude tests/docs 按需），得到调用点列表

3. **归属判定**：每个调用点的所在文件 + 函数 / 方法名，问"它在不在某个已纳入子系统的范围内？"
   - 在 → 跳过
   - 不在 → 进入候选漏检表

4. **候选漏检表（写入 panorama 末尾 `## 反向覆盖扫描结果`）**：

   ```markdown
   | 调用点 | 符号 | 调用上下文 | 当前归属 | 处置 |
   |---|---|---|---|---|
   | `run_agent.py:4362` | `_memory_write_origin = "background_review"` | _spawn_background_review 方法体内 | 未归任何子系统 | 待审 |
   | `tests/run_agent/test_background_review_summary.py` | 多处 import + 调用 | 测试文件 | 测试 | 显式排除（理由：测试不算 production 路径） |
   ```

5. **逐行处置（强制三选一）**：
   - **纳入子系统**：选择并入 S? 或新增子系统 S? +1（需重跑 1e 粒度审查）
   - **显式排除**：写理由（如"仅测试"、"已废弃"、"与主题无关"）
   - **待审**：留给 Phase 2 单独查（必须在 Phase 2 开始前回头处置，不允许跨阶段挂账）

#### 退出闸

- 表里**不允许有"待审"残留进 Phase 2**
- 若发现新的漏检子系统 → 必须把它加入候选清单，重跑 1e 粒度审查 + 一致性审查
- **此步必须在用户面前做**（不允许主代理静默归类）——见 1g 候选盲点检阅

### 1g. Phase 1 退出前候选盲点检阅 ⚠️ 人在回路

**问题**：用户拿到产物后**也判断不了"全不全"**——这是 epistemic confidence 问题，不是产物质量问题。光跑 1f 机械扫描不够，主代理可能把暴露的可疑点误判为"无需纳入"。**最后一道闸是用户。**

**机制**：Phase 1 退出前，主代理强制向用户**主动列出候选盲点**，逐条让用户拍板。

#### 主代理必产出的"盲点检阅清单"

基于 1f 反向覆盖结果 + 自己扫描时的可疑印象，列出 **3-5 条**候选盲点。每条格式：

```markdown
### 候选盲点 N: <一句话描述>
- **我看到的**：<具体的代码 / 文件 / 符号 / 调用点>，例：`run_agent.py:4284-4500` 有 `_spawn_background_review`，后台 fork AIAgent 写 memory_tool
- **我的判断**：<纳入 / 排除 / 不确定> + 理由
- **请你拍板**：纳入 S? / 新立 S? +1 / 排除（理由：...）/ NEEDS-VERIFY 留给 Phase 2 单独查
```

#### 必扫的盲点方向（每方向至少 1 条候选）

- **隐藏在大文件里的"逻辑子系统"**：大文件（>1000 行）中按方法名 / 注释段划出的"逻辑簇"
- **后台 / 异步 / 定时路径**：grep "thread"、"async"、"schedule"、"timer"、"background"、"interval"、"loop"
- **触发驱动的二次产生**：grep "on_*"、"_*_callback"、"trigger_*"、"_spawn_*"
- **测试文件名暗示的功能**：`tests/**/*<topic-keyword>*` 文件名比代码命名往往更直白，可能暴露未纳入功能
- **配置键**：`*.yaml` / `*.toml` 里包含主题关键词的键，逐个找对应实现代码

#### 退出闸

- 盲点检阅清单**至少 3 条**（少于 3 条 = 没认真找，回去扫）
- 每条**用户都已拍板**（不允许"待用户后续确认"）
- 拍板为"纳入"的盲点 → 加入候选子系统清单 → 重跑 1e 粒度审查 + 1f 反向覆盖

## 阶段 2：逐子系统深挖

对范围决议中"纳入"的每个子系统，产出一份 `02-{subsystem-slug}.md`，填**七要素卡 + 设计取舍**。

### 七要素卡必含小节

**1. `## 涉及文件`**，分三个子标题：
- `### 代码`：bullet 列表，格式 `path:line-range — 用途`
- `### 数据 / 配置`：bullet 列表，格式 `path — 格式 — 生命周期`
- `### 文档`：bullet 列表

**2. `## 生产（数据/状态是怎么被创建出来的）`**：
- 每个触发点一个 bullet：什么时候、由谁触发、写到哪里、写入什么
- 标注 `file:line` 引用
- **强制问"还有没有别的生产路径"**：grep 主要写入符号（如 `MemoryStore.add` / `memory_tool` / 各种 `_write_*`）的所有调用点，确认每个调用点都在本节列出。**漏掉任何调用点 = 本节不合格**

**3. `## 消费（被谁读，什么时候读）`**：
- 每个消费点一个 bullet：什么场景、谁读、读完做什么
- 标注 `file:line` 引用

**4. `## 存储（落到哪里）`**：
- 存储介质：文件系统 / 内存 / 数据库 / 外部服务
- 格式：json / yaml / 自定义 binary / SQLite schema / ...
- 生命周期：会话级 / 持久 / 带 TTL / 用户级 / 全局

**5. `## 分层`**：
- 如有多层（如热/冷、短期/长期、内存/磁盘）：每层一个 bullet，写存什么、访问模式
- 层间转移规则：什么时候上浮、下沉、淘汰
- 如单层就写"单层"+ 1 句说明

**6. `## 提供方式（怎么被外部模块用上）`**：
- 接口形态：HTTP API / Python 函数 / 注入 / 全局单例 / 事件 / 装饰器 / 中间件
- 调用方式：示例代码 1 段
- 使用约束：必须 / 可选 / 仅特定上下文

**7. `## 运行时形态`**（**必含**，新增）：

回答这几个问题，每条带 `file:line` 证据：

- **执行路径形态**：是同步主循环 / 异步任务 / 后台线程 / 定时触发 / 事件驱动 / 进程外服务？（可以并存——例如"主写入是主循环同步，写入后通过 on_memory_write 钩子异步镜像到 S3"）
- **触发源**：谁拉它跑？用户消息？外部 webhook？定时器？某个钩子？某个状态变化？
- **生命周期跟主循环的关系**：跟主循环一起生灭？还是独立 fork？还是常驻？
- **并发模型**：单线程？多线程？asyncio？线程池？进程池？
- **强制盲点扫描**：grep "thread"、"async"、"schedule"、"timer"、"background"、"_spawn_"、"on_<本子系统符号>" 在项目里的命中点，确认每个命中点都已纳入本节。**漏掉任何一类异步路径 = 本节不合格**

**反例（漏检触发器）**：Hermes 记忆 S1 卡如果只写"由 memory_tool 工具调用同步写入"，漏掉了 `_spawn_background_review` 触发的后台 fork 写入 → 七要素卡不合格

## 阶段 4：演进溯源（可选）

**定位**：Phase 3 结束后 skill 即算完整。本阶段是**可选挂件**，让用户按兴趣挑**一个或几个**子系统，回答"它是怎么迭代成现在这样的"。**不进主流水线退出标准**——用户不选就整阶段跳过。

**为什么放最后而不是开头**：到这一步，Phase 2 卡已把每个子系统的「涉及文件 + 入口符号 + 关键符号」精确列出。演进分析最贵的部分（"该追哪些文件/符号"）已经现成，本阶段从"探索"退化成"拿已知符号在时间轴上反向追踪"——又准又省 token。放在 Phase 0.5 会变成盲扫，token 爆且无处安放结论。

### 触发与选择 ⚠️ 人在回路

Phase 3 收尾后，主代理**主动问一句**："要不要看某些子系统是怎么迭代成现在这样的？（可选，按兴趣挑一个或几个）"

**选择本身就是本阶段唯一的人在回路点。** 主代理列出 Phase 2 子系统清单 + 一个 churn 提示帮用户选：

```bash
# 廉价预扫：每个子系统的文件近一代改了多少次，给用户当选择参考
git log --since=<上个大版本> --name-only --pretty=format: -- <S_n 的文件们> | grep -c .
```

然后给出选择参考，例："S1 近一代改了 47 次（仍在剧烈演进、故事多），S4 只改了 3 次（早已定型）——你对哪个的'怎么来的'感兴趣？"churn 高的往往最值得写进文章。

### 前置检查（否则白跑）

```bash
git rev-parse --is-inside-work-tree   # 不在 git 仓 → 本阶段不可用，提示用户后跳过
git rev-list --count HEAD             # =1 或很小 → 可能 shallow clone，提示 git fetch --unshallow
```

- **monorepo / vendored 框架**：路径必须 scope 到框架子目录，否则 churn 排名被无关代码污染。

### token 纪律：漏斗式，绝不全回溯

**核心成本认知**：`git log -p`（全量 diff）是 token 杀手，**永远配「单文件 + commit 范围」甚至 `-L 行段`，不裸跑**。聚合命令（`tag` / `shortlog` / churn 排名）输出量与历史长度无关，可放心跑全史。

```
[L1 廉价·全史安全]  tag时间线 · churn排名（仅本子系统文件）
        ↓ 锁定：哪几个文件在动
[L2 窗口·必加界]    git log --oneline <诞生..HEAD> -- <hot files>   (永远 |head)
        ↓ 锁定：哪几个 commit 是拐点
[L3 深挖·最贵]      只对拐点 commit / 单文件 / -L 行段 跑 -p / show
        ↓ 读 message + PR(#号→gh pr view) 拿 why
```

**回溯深度锚定语义边界，不是拍日历**：取"子系统诞生 commit .. HEAD"或"上个大版本 .. HEAD"中较短者，**不回溯到仓库开天辟地**。

### 每个选中子系统的执行流程（复用卡证据，不重新探索）

```
[1] 从 02-{slug}.md 取锚点：涉及文件清单 + 入口符号 + 关键符号（已现成）

[2] 定演进窗口
    git log --diff-filter=A --oneline -- <该子系统文件>   # 子系统诞生 commit
    窗口 = 诞生 commit .. HEAD（或上个大版本..HEAD，取较短者）

[3] 子系统内 churn 排名（只在它自己的文件里排，不扫全仓）
    git log <window> --name-only --pretty=format: -- <该子系统文件> \
      | sort | uniq -c | sort -rn
    分出：高 churn=演进发生地 / 零 churn=自诞生稳定

[4] 对高 churn 文件 + 入口符号，pickaxe 定位拐点（输出就几条）
    git log -S "<入口符号>" --oneline -- <file>
    git log -L <关键方法行段>:<file>     # 只追关键方法历史，token 省一个量级

[5] 只对拐点 commit 拉 why
    git show <hash> --stat            # 先预览体量
    git log -1 <hash> --format='%B'   # commit message
    gh pr view <PR#>                  # message 里 #号 → PR 讨论（why 富矿）
    # 再 grep CHANGELOG / ADR 里该子系统关键词，补人工叙事
```

### `04-evolution-{slug}.md` 必含小节

- `## 演进总览`：一句话——这个子系统是**一次成型**还是**迭代而来**？经历几次大改？
- `## 演进时间线`（**必含 Mermaid `timeline` 或 `gitGraph`**）：诞生 → 每个拐点（版本/日期/commit）→ 现状
- `## 拐点详解`：每个拐点一段——改了什么（`file:line` / commit-hash）+ 为什么（ADR/PR/message 引用）+ 留下的疤痕（兼容层 / 弃用残留）
- `## 稳定性标注`：哪些文件/设计自 vX 起未变（= 写文章可放心下结论）、哪些仍在 churn（= 谨慎，可能很快过时）
- `## 回填 Phase 2 设计取舍`：把演进发现接回 `02-{slug}.md` 的"设计取舍"段——**区分哪些取舍是深思熟虑、哪些是历史包袱**。这是本阶段对文章写作最值钱的输出。

### 验证（可选，轻量）

本阶段可选不强制跑验证子代理。若跑，复用「验证机制」的子代理模板，新增一类事实声明核对：**commit-hash / 版本号是否真实可查**（`git cat-file -t <hash>` / `git tag -l <ver>`）。报告产物 `04-evolution-{slug}-verification.md`。

### 退出标准（每个选中子系统）

- 时间线图画完 + ≥ 1 个拐点带 **commit-hash** + why 证据（ADR/PR/message）
- 所有 commit-hash / 版本号 / `file:line` **真实可查**（沿用命根子：不猜，每条带证据）

- **该子系统 `04-*.md` 落盘后已重跑 `build_view.py`**，`view.html` 增量更新

### 不允许的反模式

## 自动化 HTML 视图导出（Phase 通用）

**问题**：拆解阶段产出十几个 markdown 文件（panorama / amendments / 6 张 02-* 卡 + 7 张 verification 报告 / synthesis），单看一份累，跨份对照更累。markdown 视觉表达力 = 1990 年代水准，无法做"状态 dashboard / 可筛 table / 可点击架构图"等高密度阅读所需的交互。

**机制**：每阶段退出后**强制**把所有 .md 中的语义化数据抽出来，渲染成单页面 HTML（`view.html`）。markdown 仍是真相源，HTML 只是 view 层。

### 核心设计原则

1. **markdown 即真相源**——所有内容先写进 .md，HTML 只读不改
2. **约定式标题 = 数据契约**——本 skill 规定的所有"必含小节"标题文本不允许擅改；parser 靠标题识别段类型分发到 component
3. **单文件可双击**——一个 `view.html`，浏览器双击即开，无需 server，无需 build step
4. **零本地依赖**——`build_view.py` 仅用 Python stdlib；浏览器端 Mermaid/Marked 走 CDN
5. **不破坏性**——重生成前先备份旧 `view.html.bak`，方便对比

| 触发点 | 何时跑 | 是否硬退出闸 |

## 通用执行守则

1. **每阶段必产出 markdown 文件**。不靠对话记忆，靠文件。下次会话直接 Read 文件就能继续。
2. **退出标准必须满足才能进下一阶段**。中途想跳，先回到上一阶段补完。
3. **人在回路环节禁止自动通过**：
   - 阶段 0 关键词最终敲定
   - 阶段 1 的 1c 差异决议
   - 阶段 2 的设计取舍
   - 阶段 3 的"一句话本质"
4. **遇到不确定** → 严格走核心基础原则的决策顺序：先 Read 文件，扩大搜索范围都找不到再问用户；任何阶段性猜测必须用 `[待澄清: ...]` 显式标注。
5. **`file:line` 引用要养成习惯**——所有"谁读谁写"的描述都附上代码定位，方便用户回查；没有引用的结论 = 没依据的猜测。

❌ 不要把"读了文件"等同于"理解了"。读完要能口头复述。
❌ 不要让 Claude 自动决定范围。范围决议必须用户拍板。
❌ 不要在阶段 1 就开始写文章草稿——分享文章是 skill 结束之后的事。
❌ 不要把"代码搜索命中表"当成"理解"。命中只是入口，要 Read 上下文。
❌ 不要省略"项目专属词汇"步骤——这是 1b 关键词不漂的保险。
❌ **不要靠先验知识/同类框架经验填空**——见核心基础原则。每个结论都要回答"我从哪个文件第几行读到的？" 答不上来的不写。
❌ **不要只输出文字+表格不画图**——见可视化产出强制要求。每阶段必含图，无图不过线。
❌ **不要画无标签的箭头**——无标签的边等于不知道关系是什么，必须打回重画。
❌ **不要把"懒得读那个文件"伪装成"假设"**——见假设清单准入闸。文件能 5 分钟内 Read 验证的，不准写进假设清单。
❌ **不要用约数代替精确计数**——`~50`、`大约`、`几十次`、`~170+` 都是约数，必须改成 `rg -c` 的精确输出。
❌ **不要让薄薄一层的"功能暴露面"独立成子系统**——见 1e 粒度审查。无独立设计意图的，提议并入它所依赖的子系统。
❌ **不要拖到 Phase 3 才尝试一句话总结**——Phase 1 必须写"核心抽象草稿 (v0)"，写不出来 = 阶段 1 没真正过线。
❌ **不要把方法论当单向流水线跑**——见阶段间回顾机制。每完成一阶段或里程碑都要回头看上游产物，不主动回头 = 错误堆积。
❌ **不要在 Phase 2 卡里填"对 v0 无影响"占位**——4 行回顾必须实际填出哪些被支撑、哪些没被覆盖；全"无"通常是没认真比对。
❌ **不要跳过子代理验证**——见验证机制。规则补不完，验证才是事实一致性的最后一道闸。
❌ **不要用主代理自验证**——同上下文 = 同盲区，等于没验证。必须用独立子代理。
❌ **不要只修 [BLOCKER] 跳过 [MUST-FIX]**——常见偷懒模式：拿到报告只看 🔴 标签的就以为修完了，⚠️ 选择性忽略。结果错误累积到下一阶段。
❌ **不要让验证报告含"已修"字样**——verification.md 是子代理的客观快照，不应被改。修补记录另写到卡或独立 fixes 文件，保持验证报告与回填记录两份独立产物。
❌ **不要忘记 Phase 2 完成后跑一次 panorama 跨文档复验**——单文档内核对永远抓不到 panorama 归属错（如 `_format_memory_result` 错配给 S2 这种），cross-check 才行。
❌ **不要让跨文档检验只比文件路径**——必须深入到行号 + 符号名。两个文档都写 `acp_adapter/tools.py` 看着一致，但一个写 `:582 _format_memory_result`、一个写 `:551 _format_session_search_result` 就是真冲突。
❌ **不要让 [NEEDS-MANUAL-VERIFY] 默默积累**——所有 NEEDS-VERIFY 必须有显式处置（查证/问用户/暂搁+理由），不准跨阶段累积。
❌ **不要偷偷绕过验证者建议**——主代理用了不同的修法时必须在 `## Rejected verifier findings` 里写理由，不允许悄悄换数字或换措辞当作"修了"。
